    TID 750 (main): ~25-34% of total 2-core capacity
    TID 804:        ~28-39%

  The remaining threads and services contributed little. BusyBox top's per-thread

    TID 804: user 293942, system 34324

  TID 958 began ~10.8 seconds after the main thread (starttime ticks 1868 vs

    TID 750: voluntary 2521, involuntary 1535422
    TID 804: voluntary 226,  involuntary 1519034

  All three stayed runnable and were preempted repeatedly. In 500 reads per

  their user-space PCs or exclude short system calls.

CODE AND DEBUGGER FINDINGS
- chitu at 0x188ac calls 0xbd980 (app UI update), then 0x145e8c
  (LVGL lv_timer_handler), then branches directly back to 0x188ac. There is
  no sleep, wait or yield between iterations. This explains the hot main thread.
- With the printer idle, gdbserver briefly attached to PID 750 three times,
  sampled the hot threads, and detached each time. TID 804 was sampled in
  chitu 0xd5468 and adjacent pthread_mutex_lock/unlock code. Function 0xd542c
  is camera_interface_scan_routine (the thread creation assertion names it).
  At 0xd5470 it reads camera_flags at 0x303200, and at 0xd547c-0xd5480 it
  loops back to 0xd5468 while bit 0 is set, with no delay. The live flag was 1,
  so this is the path it was taking. The routine has a 1-second usleep at
  0xd5530 for its other path, but that path is bypassed here.
- TID 958 was sampled repeatedly at libc poll() syscall 0xb4555bf8. Its
  registers were r1=2 (two descriptors) and r2=0 (zero-millisecond timeout).
  chitu 0xea414 calls poll at 0xea434 with these exact values and branches
  from 0xea440 directly back to 0xea428 when poll returns zero. This is the
  UDP service initialized at 0x8190c with port 0x300c = 12300. The second
  descriptor is a wakeup pipe. The zero timeout explains the very high system
  time and almost absent voluntary context switches.
  Port 12300 is a separate proprietary Chitu binary service: frames start
  with 0xab, carry a length and two checksum bytes, and dispatch to callbacks.
  The built-in callback at 0xeb0bc handles 0xe0-family device queries. The
  live service had no registered device entries (list at object+0x4c empty).
  Its user-facing purpose is unconfirmed; ordinary SDCP discovery/control
  uses UDP 3000 and TCP 3030 instead.
- The UI's CPU meter (sgsys.c) is a two-second /proc/stat delta across both
  cores, with idle + iowait excluded from busy time. Its ~100% reading agrees
  with top; it is not a meter calculation error.

CONCLUSION / NEXT STEP
- This is a stock firmware CPU saturation issue. The present mod is not its
  cause; disabling libsgtap and reflashing stock were tested earlier.
- Three concrete fixes to evaluate in a customer-volume-only patch: pace the
  main UI loop by a few ms; wait or sleep in the camera scan branch where flag
  bit 0 is set; give UDP poll a short nonzero timeout (the wakeup pipe should
  retain prompt responses). Measure CPU, UI latency, camera and SDCP/UDP
  behaviour on a test image before using it for printing.
- gdbserver detached and exited; chitu remained PID 750 and job.active=0.
