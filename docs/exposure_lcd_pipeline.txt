CONTINUED (same day, printer on again) - RESULT: the filter / mask pipeline is NOT reachable in normal operation of V1.5.9
  - On the printer (read-only): no filter-*.bin anywhere (only fw_ble_scan_ad_filter.bin of the Wi-Fi/BLE chip), /customer/resources has only
    exposure_test_image0/1/2.bin; the app logs have 0 "print_file_image_filter" lines.
  - The print object init 0x7caf8 (called once, from 0x43ab4) starts worker threads: with options bit 0 clear (the normal case) the compress
    worker 0x729a8 and the send worker 0x74404; with bit 0 SET the variant 0x732d4 + 0x76198 (the mask / filter worker) + 0x729a8.
    "options" (log "layer = 0 options = 0", stored at P+0x2a8) is computed at 0x43a84 as 0 or 8 only (8 when a UI setting at +0x625 and
    +0x728 > 0, probably time-lapse): bit 0 can never be set -> the filter worker 0x76198 is never started in a print.
  - filter_routine 0x60204 (USB serial "M103" jig, writes filter-%d.bin) starts a helper 0x595b0 that creates the same compress / send
    threads (names "image_fpga_compress", "image_send") = it shows images on the LCD while it measures: a FACTORY calibration flow.
    Its init 0x60db8 (creates filter_thread) has no caller and no pointer to it in this build. The firmware also has a factory mode
    (U-Boot env chitu_factory_mode=1, checked at 0x59a60 via /etc/fw_printenv) which we must not touch (never fw_setenv).
  - So: no hidden compensation map is active, and none can be supplied by a file: the code that would read it never runs. Turning it on
    would mean patching chitu (like tools/patch_cpu.py) to set options bit 0 AND knowing the table format: research with a real risk of
    breaking printing, not recommended. The practical route stays the slicer (UVTools) or the LCD / UV power settings.

GRAY LEVELS TOWARDS THE FPGA (checked 2026-10-21 after the user pasted a Reddit PSA claiming 16K printers only get 3-bit gray, uniformity masks
being a chitu-FPGA topic; the post text was pasted by the user, the page itself could not be fetched)
  image_fpga_compress 0x729a8, mode [ctx+0x14] == 1, run-length list (value, count) per row: byte = 0x80 | floor((value >> 1) * 124 / 127)
  i.e. the app sends 7-bit gray (0..124, white = 0xFC) with run lengths, NOT 3 bits; output buffers of 0xfff bytes are handed to the sender
  through the callback dispatcher 0x55758. Another branch (first element of an empty buffer) stores 0x80 for values <= 0x7f and 0x00 above
  = a threshold, meaning not understood (possible bug, unverified). A reduction to 3 bits, if it exists, happens inside the FPGA bitstream or the
  panel interface, which cannot be seen from the app. The firmware does contain (disabled) a mask / filter pipeline + a factory USB-serial
  calibration flow (see above), i.e. Elegoo's code base has the uniformity-mask idea, but it is not active on V1.5.9.
  Empirical test idea (not done): a CTB with a gray ramp (e.g. 16 steps) and a thin-layer cure test / UV-sensitive paper, to see how many
  distinct levels the panel really gives.
  User's view (2026-10-21): the 3-bit limit is at hardware level: Chitu Systems' board / FPGA for 16K panels, while 12K boards can show shades.
  Evidence consistent with that: (a) the app has no model-specific gray reduction: image_fpga_compress has three states (0 start, 1 feed,
  2 flush) and two feed variants (run list from the CTB, raw byte buffer from a PNG path), both scale 8-bit gray to 7-bit (x 124/127) and emit
  [0x80 | gray][run length <= 72]; (b) the FPGA image ChituFPGA.bin is a Lattice Radiant bitstream for a LIFCL-17 (Nexus, 2.78 Mbit), design
  ".\Bale\plain.bit", dated 2025-02-07, "Security: On": its gray handling cannot be inspected or changed (never touched anyway);
  (c) the app logs the FPGA resolution + version at start (fpga_resolution_x/y, version) = the board announces itself. Not testable here:
  how a 12K board behaves with the same stream.

EXPOSURE TIMING AND THE LINK TO THE FPGA/MCU (read-only RE 2026-10-21, for the temporal anti-aliasing idea: several binary images inside one exposure)
  The idea (user): show the normal layer for part of the exposure, then variants with fewer edge pixels for the rest, so edge pixels get 40/60/80/100 %
  of the dose from black/white images only (bit-plane PWM). Findings:
  - Exposure is timed by the APP, polled: print step handler (print-step 0x7cfb4 area): "printer start exposure" log, 0x81228(P+0x380) (starts the
    strain recorder), 0x832b8 (command 0x29 on the link), then UV: 0x81b64(2) fan, 0x81be4(2, layer PWM = u8 of P+0x248) = UV LED PWM from the SoC
    (channel 0 via 0x883a8), then P+0x338 = now_ms (exposure start). Each pass compares now_ms - P+0x338 with "cur p_time" (live float at 0x2fda88+0x28,
    seconds) x 1000: exposure_time = P+0x24c, or for TRANSITION layers a graded time ("tran layer[%d] etime", "[%d] cur p_time", from P+0x168 and a
    per-layer delta at P+0x3a4..). When done it goes to 0x7d170 (UV off path; 0x83304 = command 0x28, UV PWM state 1 = off).
  - The link (0x830ac select, 0x830f4 write -> 0x88ef4; fd in 0x2fe458+4) carries: 0x29 (exposure on), 0x28 (exposure off), 0x1a (an 8-byte parameter
    command, 0x83350), and the IMAGE STREAM: 0x83690 sends the compressed layer in 0x800-byte packets, each "0x3c + 2048 bytes" (frame length 0x801).
    The send worker 0x74404 calls it per compressed chunk (log image_send_ticks ~770 ms per full layer in the Piramidi 12x log).
  - So an extra image = a new compressed stream sent as 0x3c packets + 0x29 / UV on for dt + 0x28 / UV off. Whether the FPGA keeps the previous image
    while a new stream arrives, whether 0x29/0x28 gate the LCD or only the UV, and the real timing are NOT known.
  Cost estimate: compress ~780 ms + send ~770 ms per image (probably overlapped in two threads) -> 0.8 - 1.5 s per extra image with the UV off.
  Ways to implement (increasing effort): (1) passive tracer of the link in libsgtap (interpose write/ioctl on the fd of /dev/spidev0.0 or the
  transport, opt-in file like sgcap): logs command bytes + timestamps per layer = the real sequence, no behaviour change; (2) a stub patch in chitu
  at the exposure end (like tools/patch_cpu.py) that runs extra sub-exposures: needs the extra images (extra entries in a .goo / generated on the
  printer from the layer) and the exact stream format; (3) generate everything off line and feed it through the print file. Unverified everywhere.

FIRST TRACE OF THE BOARD LINK (2026-10-22, build 32 tracer, built-in LCD test Text -> Grid -> Full screen, tank removed, UV on ~8 s each):
backups/fpga_trace_20261022_lcdtest.csv (8636 records, 31 s), summary with tools/analysis/fpga_trace.py. Frames on /dev/spidev0.0 (one thread, tid 752):
  1. "28 00 00 00", "2a 00 00 00", "2c 00 00 00" (3 x 4 bytes, same ms)  = start AND end of every display (meaning not decoded: stop / clear / reset?)
  2. IMAGE: 0x3c + 512 data bytes per packet, no gaps: 3174 / 2824 / 2581 packets = 1628262 / 1448712 / 1324053 B in 673 / 565 / 525 ms (2.4-2.6 MB/s,
     ~20 Mbit/s). The data are exposure_test_image0 / 1 / 2.bin (Text, Grid, Full screen) from byte 48 on (the 48-byte file header, whose bytes 4..7 =
     the file size, is not sent): the packet count = ceil((size - 48) / 512). First payload byte 0x00 (image0, image2) or 0x80 (image1) = start state.
  3. 8 x (0x4c + 2047 zero bytes) = 16 KB of zeros right after the image (4 ms): end-of-image / flush
  4. "29 00 00 00" = show / start the display; in the SAME millisecond the UV: 5. "fe 04 01 07 a1 07 a1" (7 bytes, answer "fe 00 00", 3 bytes)
  6. ~8 s later "fe 04 01 07 a1 00 00" (+ answer) = UV off, then 1. again (28 2a 2c).
  UV LED frame = 0xfe, 0x04, 0x01, period u16 BE (0x07a1 = 1953), duty u16 BE (0x07a1 = 100 %, 0x0000 = off) -> the app's PWM calls (0x883a8) go over this link
  (duty scaled to the period, e.g. 255 x 255 PWM = 100 %). So: DISPLAYING AN IMAGE (3c.. 4c.. 29) AND SWITCHING THE UV (fe ..) ARE SEPARATE FRAMES:
  an image can be shown with the UV off by simply never sending the fe frame (or sending duty 0).
  Stream format (test images, same as image_fpga_compress): per row [value byte 0x80|gray7][run bytes <= 72 ...] runs summing to 15120 pixels; run bytes
  sum = 94186371 ~ 15120 x 6230. Full screen = 0xfc (white) + 208 x 0x48 + remainder per row; Text / Grid also contain other gray values (anti-aliased).
  Image buffers: the byte after 0x3c is the first payload byte, so the 00 / 80 alternation (00, 80, 00) is NOT a buffer flag but each file's first value byte.
  Not known: the exact role of 28 / 2a / 2c and of the 0x4c block, whether the FPGA double-buffers (could a second image be streamed while one is shown?),
  how 0x29 picks the image, what its 3 zero bytes mean.
  Consequences for the ideas: (a) UV-off display is possible by construction (own frames: 28 2a 2c, 3c stream, 4c x 8, 29, no fe); (b) a full image costs
  0.5-0.7 s on the link; (c) dim UV for visible tests: fe .. duty = e.g. 20 / 1953 (1 %); (d) temporal anti-aliasing needs the same frames per sub-image
  (stream + 4c + 29 + UV on/off), with the UV off while streaming = +0.6 s per extra image, less if the FPGA can take the next image while one is shown (to test).

UV-OFF / DIM DISPLAY COMMAND (build 33, mods/src/sgtap/sgdisp.c, tools/lcd_stream.py, 2026-10-22)
  Stream format (decoded from the stock test images + the app's compress code): the file = 48-byte header (1d 01 fd 12, bytes 4-7 = file size LE, rest copied) + stream
  from byte 48; the stream = 12460 half rows of 7560 px (6230 rows x 2); per half row: value byte 0x80|((g>>1)*124//127) (ONE pixel) + run bytes <= 72 (more repeats of that
  value); sum of (1 + runs) over all value tokens = 15120 x 6230 exactly; the stock images add zero padding at the end and the first byte is 0x00 or 0x80 (start state).
  tools/lcd_stream.py selftest: decode + re-encode keeps the pixels of the 3 test images (minimal re-encoding is 1-2 % smaller: the app also emits redundant value tokens).
  Command and safety: see the project notes (build 33). Order of what the board sees for a show: fe..0000, 28 2a 2c, 3c packets, 4c x 8, 29 (+ fe..duty only with duty > 0).
  Unverified on the real board: that a minimal re-encoded stream shows the same picture as the stock stream, that 29 alone shows the image with the UV off, the dim levels.

FIRST lcdshow ATTEMPT (2026-10-22, build 33, "lcdshow grid 0 20", UV 0, printer idle, trace on: backups/fpga_trace_20261022_lcdshow_firstattempt.csv) - FAILED SAFELY
  The command aborted with "sending to the display board failed (stopped, UV off)". Trace: our first frame fe 04 01 07 a1 00 00 (UV off) got the answer 00 00 00 instead of
  fe 00 <status>, so the sequence stopped (no image frame was sent, the UV was never on) and the stop sequence ran (fe .. 0000, 28 2a 2c).
  CAUSE (code reading): the app has TWO SPI devices on the same fd, selected by the app's function 0x830ac(ch) (gpio 0x48): channel 0 = the display board
  (0x28 / 0x29 / 0x2a / 0x2c 4-byte frames, 0x3c image packets, 0x4c blocks, ...), channel 1 = the "fpga_extend" device that takes the 0xfe frames:
  0x83780(cmd, data, len) = [0xfe][cmd][data...] on channel 1 + 0x837f0 reads 3 bytes and expects "fe 00 <status>" (stepper control fpga_stepper_ctrl 0x83e00 uses it too;
  cmd 4 data 01 period duty = the UV PWM seen in the LCD test). Our frame went to channel 0 (the display board ignored it). FIX (build 34): dsp_uv selects channel 1 before the
  0xfe frame + the read and channel 0 again afterwards. Side effect of the failed attempt: the display board received two unknown 0xfe frames (no visible effect, the
  stop sequence followed).
